## 1. Module 1 — Từ simple graph tới agent có memory

- **Motivation + Simple Graph:** LangGraph mô hình hoá workflow thành đồ thị có hướng có thể có vòng lặp: **State** (snapshot dùng chung, thường là typed schema), **Nodes** (hàm đọc state, làm việc, trả update), **Edges** (chuyển tiếp cố định hoặc có điều kiện). Docs Graph API hiện hành (đọc 21/11/2026) mô tả đúng ba thành phần này, thực thi theo mô hình message-passing kiểu Pregel theo từng **super-step** — khớp curriculum Module 1. So với task 125: 125 dạy cùng bộ ba này qua việc dựng lại agent ReAct tự viết; khóa này dạy từ graph rỗng đi lên, hệ thống hơn.
- **LangSmith Studio:** IDE trực quan để xem/test graph local (README: chạy `langgraph dev` trong thư mục `studio/` từng module). Đây là cầu nối sang 194: Studio/tracing là nơi nhìn quỹ đạo graph, còn 194 dạy đo quỹ đạo đó bằng eval. Nội dung thao tác Studio chi tiết trong bài học: **Chưa xác định**.
- **Chain → Router → Agent:** ba nấc thang điều khiển. Chain là luồng tuyến tính (model + tools trong node); Router thêm conditional edge để rẽ nhánh theo state; Agent đóng vòng lặp llm → tool → llm (vòng ReAct của 125 §3) thành đồ thị khai báo. Bài học thiết kế: **mức tự do của agent là lựa chọn kiến trúc, không phải mặc định** — bài toán tuyến tính thì đừng trả giá vòng lặp.
- **Agent with Memory (bài cuối Module 1):** gắn checkpointer + `thread_id` để agent nhớ trong một thread. Docs Checkpointers hiện hành (đọc 21/11/2026) xác nhận: checkpointer lưu snapshot state ở mỗi super-step, tổ chức theo thread, là điều kiện bắt buộc cho human-in-the-loop, time travel, fault-tolerance và conversational memory. Đây là nền cho toàn bộ Module 2/3/5.

## 2. Module 2 — State schema, reducers, multiple schemas, quản trị messages

- **State Schema:** state không phải dict tự do mà là schema khai báo các **channel** (khóa của state). Docs Graph API (đọc 21/11/2026): mỗi channel giữ một giá trị và định nghĩa cách update merge vào; mặc định last-write-wins, channel có reducer thì combine (vd append vào list). Schema định nghĩa bằng TypedDict/dataclass/Pydantic (Python) — khớp bài State Schema.
- **State Reducers:** reducer là hàm hai ngôi (left = giá trị hiện tại, right = update từ node) quyết định cách merge từng khóa. Đây là khái niệm team đã gặp ở 125 (reducer `operator.add` cho messages, reducer tùy biến thay-thế-theo-id để sửa message) và 127 — khóa này dạy nó như một bài riêng, có hệ thống: **thiết kế reducer sai thì parallel branch ghi đè nhau**, đúng cảnh báo của beri.net ("design state schemas and reducers so parallel branches merge correctly").
- **Multiple Schemas:** docs hiện hành xác nhận hai nhu cầu: (a) private channels mà node nội bộ chia sẻ nhưng không thuộc input/output của graph, (b) input/output schema là tập con của state nội bộ đầy đủ. Đây là cơ chế đóng gói: graph phơi ra mặt ngoài hẹp, giữ state làm việc ở trong — tương đương nguyên tắc "chỉ phơi contract cần thiết" khi thiết kế extension/API.
- **Trim and Filter Messages + Summarizing:** lịch sử hội thoại dài vô hạn là kẻ thù của context window. Khóa dạy ba lớp: cắt (trim) theo số lượng/token, lọc (filter) message không cần, và tóm tắt (summarize) lịch sử cũ thành bản nén rồi lưu vào memory (bản internal) hoặc external memory (bản ngoài state). Nối 128/130: đây là tầng "quản trị working memory" trước khi tới long-term memory ở Module 5 — lưu cái gì và lấy lại cái gì (hai câu hỏi trục của 127 §1) được trả lời ở tầng messages trước.

## 3. Module 3 — Streaming, breakpoints, human feedback, time travel

- **Streaming:** phát tín hiệu khi graph đang chạy thay vì chờ kết quả cuối — điều kiện để giám sát và can thiệp kịp thời (đã gặp ở 125 §5). Docs Interrupts hiện hành bổ sung: khi dùng event streaming, payload của `interrupt()` hiện qua stream interrupts và cờ interrupted — tức là streaming và human-in-the-loop là một cặp.
- **Breakpoints (static) vs Dynamic Breakpoints (`interrupt()`):** đây là điểm khóa dạy kỹ hơn 125. Docs Interrupts (đọc 21/11/2026) phân biệt rõ: **static breakpoints** dừng trước/sau node cố định khi compile (`interrupt_before`/`interrupt_after` — cơ chế 125 §6 dùng), còn **`interrupt()`** là dynamic: gọi ở bất cứ đâu trong node, có thể có điều kiện theo logic ứng dụng, payload phải JSON-serializable, graph lưu state qua checkpointer và chờ vô hạn tới khi resume bằng `Command(resume=...)` trên cùng `thread_id`. Khóa có bài riêng cho từng loại (Lesson 2 Breakpoints, Lesson 4 Dynamic Breakpoints) — đúng thứ tự docs khuyến nghị: cổng cứng ở ranh giới node trước, cổng mềm theo điều kiện sau.
- **Editing State and Human Feedback:** tại điểm dừng, người đọc state (`get_state`), sửa state (`update_state` — docs Checkpointers: tạo checkpoint mới, không sửa checkpoint cũ, update đi qua reducer như node update, có thể chỉ định `as_node` để quyết định node chạy tiếp), rồi resume. Đây là hiện thực hoá cổng duyệt "ngay trước hành động có tác dụng phụ" của 125 §6 thành quy trình đầy đủ: dừng → xem → sửa → chạy tiếp.
- **Time Travel:** docs Checkpointers xác nhận: replay từ checkpoint cũ (invoke với `checkpoint_id` của snapshot trong `get_state_history`), node trước checkpoint bị bỏ qua, node sau chạy lại (kể cả LLM call và interrupt sẽ trigger lại); cũng fork được state tại checkpoint bất kỳ để thử quỹ đạo khác. Giới hạn quan trọng: chỉ resume được từ ranh giới super-step (checkpoint), không phải giữa node. Ánh xạ sang team: đây là bản tự động hoá của việc "quay lại commit cũ, rẽ nhánh thử cách khác" mà team làm bằng git — graph có lịch sử checkpoint như repo có lịch sử commit.

## 4. Module 4 — Parallelization, sub-graphs, map-reduce, Research Assistant

- **Parallelization + Map-reduce:** docs Graph API: `Send` dynamically invokes nodes for fan-out — một node phát nhiều `Send` để chạy song song nhiều nhánh (map), reducer ở channel đích gộp kết quả (reduce). Đây là chỗ Module 2 (reducer) trả bài: không có reducer đúng thì fan-out song song sẽ ghi đè mất kết quả. Mẫu này nối trực tiếp cách team chia việc: một task lớn tách thành nhiều nhánh độc lập, kết quả gộp về một chỗ có kiểm chứng.
- **Sub-graphs:** graph lồng trong graph — node của graph cha là một graph con hoàn chỉnh, có state/checkpoint riêng (docs Checkpointers: `checkpoint_ns` dạng `"node_name:uuid"`, lồng nhiều tầng nối bằng `|`). Sub-graph là đơn vị tái sử dụng và đóng gói: graph con có schema riêng (multiple schemas, Module 2), graph cha chỉ thấy input/output.
- **Research Assistant (dự án Module 4):** ghép parallelization + sub-graphs + map-reduce thành một assistant nghiên cứu (theo curriculum + beri.net; bài này dùng Tavily cho web search theo README). Chi tiết kiến trúc assistant trong notebook: **Chưa xác định** (không chạy/đọc notebook). Nhưng vị trí của nó trong lộ trình rõ ràng: đây là bài "ghép mọi thứ đã học thành một hệ thống" tương đương Essay Writer của 125 và email agent của 127 — khóa nào cũng kết bằng một dự án ghép, không kết bằng lý thuyết rời.

## 5. Module 5 — Long-term memory: Store, Profile, Collection

- **Short vs Long-Term Memory:** docs Persistence (qua search 21/11/2026) xác nhận hai hệ thống bổ sung: **Checkpointers** persist state của một thread (short-term, thread-scoped: conversation continuity, human-in-the-loop, time travel, fault tolerance) và **Stores** persist dữ liệu ứng dụng tự định nghĩa ngoài graph state (long-term, cross-thread: user preferences, facts, shared knowledge). Hầu hết ứng dụng dùng cả hai. Đây đúng khung checkpointer-vs-store của 127 §3, nay được dạy từ chính khóa nền tảng.
- **LangGraph Store:** store là key-value theo namespace + key, tiêm vào node qua tham số store khi compile (`compile(checkpointer=..., store=...)`). Sai lầm kinh điển (127 §3): lưu sở thích người dùng theo thread thay vì theo user — đổi thread là trắng. Store khóa theo namespace (thường là user_id) mới đúng tầng.
- **Memory Schema + Profile vs + Collection:** hai mẫu tổ chức bộ nhớ dài hạn. **Profile** = một tài liệu duy nhất về người dùng, cập nhật tại chỗ (sự kiện ổn định: tên, sở thích, vai trò). **Collection** = nhiều tài liệu rời, mỗi tài liệu một mẩu nhớ, truy xuất bằng tìm kiếm (sự kiện rời rạc, tiền lệ). Đối chiếu 127: profile ≈ semantic memory dạng hồ sơ; collection ≈ semantic/episodic dạng tập tài liệu tìm được. Khóa dạy cả hai vì không có mẫu nào đúng cho mọi loại nhớ — chọn theo hình dạng dữ liệu, không theo thói quen.
- **Build an Agent with Long-Term Memory:** ghép store + schema thành agent nhớ qua nhiều phiên. Nối 128/130: agent memory không nằm trong model mà nằm ở hệ thống quanh model (code lấy ra, đặt trước mặt model) — nguyên tắc 127 đã chốt, khóa này cho thêm mẫu schema cụ thể để áp dụng.

Không phát hiện lệch pha kiểu 191 (khóa dạy transport cũ). Điểm cần lưu ý duy nhất là Module 6 không thấy trên trang khóa hiện hành (mục Ghi chú trung thực).
- **Vendor-specific vs portable:** khóa là đào tạo của chính LangChain cho framework của họ (beri.net nhận xét thẳng: "teaches the LangChain way rather than comparing frameworks"). Công cụ (Studio, LangSmith Deployment, Store API) là của LangChain; nhưng **mẫu tư duy** — state có schema + reducer, checkpoint theo thread, cổng duyệt trước hành động, fan-out/fan-in có reducer gộp, hai tầng nhớ thread/user — mang sang framework khác và sang quy trình team được. Team đã học cùng mẫu trên nền khác ở 125/127 (DeepLearning.AI), 128 (Oracle), 130 (Letta/MemGPT) — khóa này là bản gốc chính thức để đối chiếu các bản kia có dạy lệch không.
- **Nối 125/127:** 125 dạy agent ReAct + persistence + human-in-the-loop ở mức short course (~1h47); khóa này sâu hơn hẳn (~6 giờ, 55 bài): thêm multiple schemas, trim/summarize messages, dynamic breakpoints, time travel, parallelization/map-reduce/sub-graphs, profile-vs-collection — đúng các mảng 125 §9 để trống. 127 dạy long-term memory qua LangMem + email agent; khóa này dạy tầng Store/schema nền mà LangMem xây trên đó. Học xong khóa này, mạch LangGraph của team coi như đủ ba tầng: dựng graph (196) → nhớ dài hạn (127) → đo agent (194).
- **Nối 191 (MCP) + 194 (eval):** node trong graph là nơi gọi tool — tool đó có thể là MCP tool (191); checkpoint/trace là nơi kiểm chứng quỹ đạo gọi tool — evaluator quỹ đạo của 194 (`schema_before_query`) áp dụng nguyên vẹn lên trace của graph. Ba khóa ghép thành một mạch hoàn chỉnh: **dựng (196) → nối tool chuẩn (191) → đo (194)**.

## 8. Áp dụng cho team muse-teamwork và nhà máy (đề xuất có điều kiện, không tự làm)

1. **Chưa dựng LangGraph cho team.** Lý do như 194 §7: team chưa có agent sản phẩm chạy traffic thật; "graph" của team hiện là quy trình GitHub task file (open → claimed → doing → review → done) với checkpoint là commit, thread là task id, breakpoint là cổng review của muse-main. Quy trình đó đang làm đúng vai của LangGraph ở tầng con người + agent chị cả. Dựng thêm framework lúc này là thêm hạ tầng không có bài toán.
2. **Mượn 4 mẫu áp dụng ngay bằng quy trình hiện có:** (a) **reducer cho STATUS/task notes** — mỗi trường chỉ có một cách merge rõ ràng (notes chỉ append, status chỉ đi theo vòng đời, không ai ghi đè tự do) — team đã làm một phần ở PROTOCOL §8, giữ nguyên và gọi đúng tên; (b) **static breakpoint trước hành động có tác dụng phụ** — merge/push main/device test luôn dừng ở cổng muse-main (đã có §4), không để worker tự chạy qua; (c) **time travel bằng git** — mọi trạng thái task đều quay lại được theo commit, fork branch thử cách khác thay vì sửa đè main (đã có §2 branch-per-task); (d) **profile vs collection cho bộ nhớ team** — hồ sơ người dùng ổn định (USER.md/MEMORY.md dạng profile) tách khỏi tập ghi chép rời tìm được (memory/ dạng collection) — đúng cấu trúc hiện tại, khóa này cho team ngôn ngữ để gọi tên và giữ ranh giới đó.
3. **Ánh xạ nhà máy (gợi ý, không tự làm):** nếu sau này có trợ lý tra cứu SOP/FSSC hoặc hỗ trợ lịch sản xuất, kiến trúc đúng theo khóa là: state có schema (ca, line, sản phẩm, ràng buộc), node tra cứu tài liệu trước node trả lời (reducer/checkpoint để truy vết), breakpoint bắt buộc trước mọi đề xuất đổi lịch (người duyệt sửa state rồi mới chạy tiếp), store theo người dùng/ca (profile: vai trò, line phụ trách; collection: tiền lệ xử lý sự cố), và nguyên tắc "Chưa xác định thay vì đoán" tương ứng evaluator kiểm tra agent có dừng hỏi khi thiếu dữ liệu không (nối 194 §7).
4. **Không học deployment bằng cách tạo tài khoản thật:** Module 6/LangSmith Deployment cần tài khoản + có thể phát sinh chi phí theo gói — chỉ học khái niệm, không đăng ký thay Anh (đúng §9 và ranh giới "việc tốn tiền mang ra hỏi Anh" §10).
