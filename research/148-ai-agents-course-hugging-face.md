## 1. Unit 1 — Agent là vòng lặp, không phải một lần gọi model

- **Định nghĩa của khóa:** agent là hệ thống dùng một AI model để tương tác với môi trường nhằm đạt mục tiêu người dùng định nghĩa; nó kết hợp reasoning, planning và thực thi hành động (thường qua external tools). Hai phần: **Brain** (AI model — suy luận, lập kế hoạch, quyết định hành động) và **Body** (capabilities + tools — mọi thứ agent được trang bị để làm). Phạm vi hành động phụ thuộc vào "body": không có tool thì agent chỉ nói, có tool nào thì làm được việc đó.
- **Vòng lặp lõi:** Think/Thought → Act/Action → Observe/Observation, lặp tới khi xong. Thought là model quyết định bước tiếp theo; Action là gọi tool với tham số; Observation là kết quả tool được đưa ngược vào ngữ cảnh để model quyết định tiếp. Đây là dạng ReAct đã gặp ở task 125 bài 2 (tự viết bằng Python thuần + regex) — khóa này dạy cùng vòng lặp nhưng đặt tên chuẩn và đi kèm phần LLM nền (messages, special tokens, chat templates) để người học hiểu model "nhìn thấy" vòng lặp dưới dạng text ra sao.
- **Điểm phân công lao động (lặp lại từ 125/140, khóa này nói rõ nhất):** model **không bao giờ tự chạy tool**. Model chỉ sinh text trông giống một lời gọi hàm; code điều phối (orchestrator) mới parse, chạy hàm thật, rồi dán kết quả trở lại hội thoại. Model stateless nên mỗi vòng nó đọc lại toàn bộ ngữ cảnh từ đầu. Hiểu điểm này thì hiểu vì sao mô tả tool, định dạng output và giới hạn số bước quan trọng hơn "model thông minh hơn".
- **Tool là gì:** một hàm nguyên tử kèm siêu dữ liệu để mô tả cho LLM: name, description, input types + descriptions, output type (và method `forward` để thực thi). Khi khởi tạo agent, các thuộc tính này được biến thành tool description **ghim vào system prompt**. Hệ quả: chất lượng mô tả tool là một nửa của việc gọi đúng — cùng bài học task 123 (prompt/checklist rõ) và 140 §4.
- **Phổ agency:** khóa đặt agent trên một phổ tự chủ tăng dần thay vì có/không — cùng kết luận task 140 §1. Mức tự chủ càng cao (tự viết code chạy) càng cần lớp chặn mạnh hơn, dẫn thẳng tới §3 dưới đây.
- **Ánh xạ sang team:** vòng làm việc của worker trong team chính là Thought/Action/Observation ở quy mô hệ thống: đọc task file + STATUS (observation), quyết định bước tiếp theo (thought), gọi git/script/browser (action), đọc output rồi quyết tiếp. Khác biệt: team ghi observation vào **hiện vật bền** (task file, commit) thay vì chỉ giữ trong transcript — nên vòng lặp của team truy vết được sau khi phiên làm việc kết thúc, đúng lý do team chọn GitHub làm nguồn sự thật (PROTOCOL §1).

## 2. Unit 2 — Ba framework, một vòng lặp: chọn theo hình dạng bài toán

Khóa cố ý dạy 3 framework cạnh nhau thay vì bán một framework là cách duy nhất. Điểm chung cả ba đều phải giải quyết: LLM engine, danh sách tools, parser trích tool call từ output, system prompt đồng bộ với parser, memory, và error logging/retry (vì model sẽ sai). Điểm khác là **trọng tâm thiết kế**:

| Framework | Trọng tâm | Dạng agent/tool tiêu biểu | Hợp khi nào |
|---|---|---|---|
| smolagents (2.1) | Code-first, tối giản (thư viện nhẹ, khoảng 1.000 dòng theo trang khóa) | `CodeAgent` (viết Python), `ToolCallingAgent` (viết JSON), `@tool` | Prototype nhanh, hệ sinh thái Hugging Face, muốn code-as-action |
| LlamaIndex (2.2) | Data-first: agent trên dữ liệu của bạn bằng indexes + workflows | AgentWorkflow, FunctionTool/QueryEngineTool | Bài toán nặng về RAG/truy xuất tri thức, nhiều nguồn dữ liệu |
| LangGraph (2.3) | Control-first: đồ thị trạng thái, kiểm soát luồng | StateGraph: nodes/edges/conditional edges (task 125) | Workflow nhiều bước cần rẽ nhánh, dừng chờ người duyệt, bền trạng thái |

- **Khi nào không cần framework:** khóa nói thẳng — việc đơn giản dạng chain/router thì viết code thuần tốt hơn vì kiểm soát và hiểu hệ thống hơn; abstraction chỉ đáng khi xuất hiện tool calling động, vòng lặp nhiều bước do LLM quyết, hoặc quản lý trạng thái qua nhiều lượt. Đây là cùng tiêu chí "workflow xác định vs agent" ở task 145/146/147: đừng trả chi phí framework cho việc một script thẳng làm được.
- **Ánh xạ sang team:** team hiện **không dùng framework agent nào** cho việc phối hợp — task file + git + hub tự xây đóng vai runtime, và mỗi worker là một agent "code-first" theo nghĩa đen (viết code, chạy tool thật). Khóa xác nhận lựa chọn này ở tầng nguyên lý: framework chỉ đóng gói vòng lặp + parser + memory; team đã có các mảnh đó ở dạng quy trình (PROTOCOL = system prompt, script claim/complete = parser/tool, task file = memory bền). Thêm framework bây giờ là thêm abstraction không có bài toán tương ứng.
- **Ánh xạ sang nhà máy (gợi ý, không tự làm):** nếu sau này Anh muốn một trợ lý tra cứu SOP/checklist FSSC, hình dạng bài toán là "agent trên dữ liệu của mình" — đúng trọng tâm LlamaIndex/RAG, không phải LangGraph hay smolagents. Chọn framework theo dữ liệu trước, theo độ quen tay sau.

## 3. smolagents — CodeAgent vs ToolCallingAgent và bài toán sandbox

- **Hai loại agent:** `CodeAgent` (mặc định) viết tool call dưới dạng **Python code snippet** rồi thực thi; `ToolCallingAgent` viết tool call dưới dạng **JSON có cấu trúc** (dạng phổ biến của OpenAI API) mà hệ thống parse. Cả hai đều cần `model` + `tools` lúc khởi tạo, đều kế thừa vòng lặp nhiều bước Thought → tool call → execution.
- **Vì sao code thắng JSON (luận điểm trung tâm của smolagents, dựa trên paper *Executable Code Actions Elicit Better LLM Agents*):** (1) *Composability* — lồng/gọi lại hành động như hàm Python, JSON không lồng được; (2) *Object management* — giữ output phức tạp (ảnh, bảng) trong biến, JSON chỉ chứa text; (3) *Generality* — code biểu đạt được mọi việc máy tính làm được, kể cả vòng lặp/điều kiện; (4) *Representation in LLM training corpus* — code chất lượng cao đã có sẵn nhiều trong dữ liệu huấn luyện. Hệ quả thực hành: ít bước hơn, ít lượt gọi model hơn cho cùng một việc — đúng so sánh JSON plan vs code-as-action ở task 140 §6, nhưng khóa này chọn phe code và đầu tư vào sandbox để trả giá an toàn.
- **Giá phải trả — thực thi code do LLM sinh:** tài liệu chính thức liệt kê 4 nguồn rủi ro: lỗi vô ý của LLM, supply-chain (model không tin cậy), prompt injection (agent duyệt web gặp trang độc), và lạm dụng agent công khai. CodeAgent mặc định chạy code trong môi trường của bạn — "inherently risky". Đây là năng lực nguy hiểm nhất của khóa, giống kết luận task 143 §6 về code execution của AutoGen.
- **Lớp chặn 1 — LocalPythonExecutor:** smolagents không dùng Python interpreter gốc mà tự xây interpreter chạy theo AST từng operation: imports bị cấm mặc định trừ khi nằm trong danh sách được phép (`additional_authorized_imports`), submodule bị tắt mặc định (kể cả đường vòng kiểu `random._os`), tổng số operation bị chặn trần để chống vòng lặp vô hạn, operation chưa định nghĩa thì báo lỗi. Tài liệu nhấn mạnh: **không sandbox local nào an toàn 100%** — package được phép vẫn có thể bị lạm dụng (vd tạo hàng nghìn file ảnh lấp ổ đĩa).
- **Lớp chặn 2 — sandbox từ xa:** hai cách: (a) chỉ chạy từng snippet trong sandbox (E2B/Docker, `executor_type="e2b"`/`"docker"`) — đơn giản nhưng không hỗ trợ multi-agent và phải truyền state qua lại; (b) chạy toàn bộ hệ agent trong sandbox — cách ly tốt hơn nhưng phải đưa credentials vào sandbox. Trade-off rõ: cách ly càng mạnh, setup càng nặng và càng nhiều bí mật phải di chuyển.
- **Ánh xạ sang team:** worker của team cũng là "code agent" — viết code rồi chạy thật (build extension, chạy validate, push branch). Lớp chặn tương đương của team nằm ở tầng quy trình thay vì interpreter: chỉ chạy trên branch feature, chỉ trong repo được giao, không tự merge lên main (PROTOCOL §4), và claim có hạn 2h + watchdog chống kẹt (§7) đóng vai "trần số operation". Khóa cho ngôn ngữ để gọi tên: `additional_authorized_imports` của smolagents tương đương danh sách tool/đường dẫn được phép trong từng task của team — việc nào không nằm trong danh sách thì không được chạm, dù model "nghĩ ra" cách làm.

## 4. Multi-agent trong smolagents — phân cấp bằng managed agents

- **Cơ chế:** bọc một agent con thành managed agent với `name` + `description` bắt buộc; mô tả đó được ghim vào system prompt của manager agent **giống hệt cách mô tả tool** — manager gọi agent con như gọi một tool. Ví dụ khóa: manager (CodeAgent, lo planning + tổng hợp) quản lý một web search agent (ToolCallingAgent với search + visit webpage tool, `max_steps` cao hơn vì duyệt web cần nhiều vòng).
- **Chọn loại agent theo vai:** việc duyệt web một mạch, không cần gọi tool song song → ToolCallingAgent (JSON) là đủ; việc lập kế hoạch/suy luận/sáng tác code → CodeAgent. Đây là chi tiết thiết kế đáng nhớ: trong cùng một hệ, **mỗi vai chọn dạng action rẻ nhất đủ dùng**, không mặc định mọi agent đều code.
- **Ánh xạ sang team:** team 3 Muse là cùng mẫu phân cấp (task 140 §7, 143 §7) nhưng với hai khác biệt có chủ ý: (a) "manager" của team là chị cả + Anh (người chốt hướng, ranh giới quyết §10), không phải LLM tự giao việc qua system prompt; (b) kênh giao việc là task file bền có trạng thái rõ, không phải lời gọi hàm trong bộ nhớ. Ưu điểm của cách team: truy vết và khôi phục sau sự cố (worker chết giữa chừng vẫn còn branch/commit — bài học task 112). Ưu điểm của smolagents: nhanh, ít nghi lễ — hợp cho bài toán trong một tiến trình, không hợp cho việc có hậu quả thật như merge/push.
- **Bài học rút ra:** mô tả agent con (`name` + `description`) quyết định manager giao việc đúng hay sai — tương đương mô tả vai trong PROTOCOL §9/§10 của team (Ú build, Vịt research, chị cả quản lý). Vai càng rõ, giao việc càng ít lệch.

## 5. Unit 3 — Agentic RAG: retrieval là một tool, không phải một bước cố định

- **Giới hạn của RAG truyền thống (khóa nêu 2 điểm chính):** (1) chỉ truy xuất **một lần** — kết quả lần đầu tệ thì câu trả lời tệ theo; (2) độ tương đồng ngữ nghĩa tính với **câu hỏi của người dùng** (thường ở dạng nghi vấn) trong khi tài liệu chứa đáp án thường ở dạng khẳng định — điểm tương đồng bị hạ, dễ hụt tài liệu đúng.
- **Cách agentic RAG sửa:** biến retriever thành một **tool** trong vòng lặp agent. Agent tự (a) **diễn đạt lại truy vấn** cho gần với tài liệu đích (gần kỹ thuật HyDE), (b) **đọc kết quả rồi truy xuất lại** nếu chưa đủ (gần self-query refinement), (c) gọi retriever 0, 1 hoặc nhiều lần tùy câu hỏi, và (d) kết hợp retriever với tool khác (web search, tính toán, lịch...). Use case của khóa: Alfred tổ chức gala cần trả lời về khách mời (nền tảng, sở thích), kiến thức thể thao/văn hóa/khoa học để tiếp khách, tránh chủ đề chính trị/tôn giáo, và cập nhật thời tiết thời gian thực cho màn pháo hoa — một câu hỏi có thể cần truy xuất nội bộ, câu khác cần web, câu khác không cần truy xuất gì cả.
- **Chi phí đổi lại:** mỗi quyết định "có truy xuất không, truy xuất gì, đã đủ chưa" là thêm lượt gọi model — chậm hơn và tốn hơn RAG một bước, và vòng lặp phải có trần. Chỉ đáng khi câu hỏi thật sự đa dạng/nhiều nguồn; câu hỏi đơn giản một nguồn thì RAG cố định rẻ và đoán được hơn (cùng quy tắc chọn ở task 146 §4: việc rõ bước → workflow xác định).
- **Ánh xạ sang team:** worker làm research đang chạy agentic RAG bằng tay mà chưa gọi tên: đọc task → tự diễn đạt truy vấn tìm kiếm → đọc kết quả → tìm lại với truy vấn khác → đối chiếu repo/task cũ → mới viết báo cáo. Các báo cáo 125–147 đều có mục "quét chống trùng" chính là bước truy xuất nội bộ trước khi ra web. Khóa gợi ý một cải tiến rẻ: ghi rõ trong báo cáo research **truy vấn nào đã thử và vì sao truy xuất lại** — hiện báo cáo chỉ liệt kê nguồn cuối, không ghi quá trình sửa truy vấn. Đây là đề xuất có điều kiện ở §8, không tự đổi mẫu báo cáo.
- **Ánh xạ sang nhà máy (gợi ý, không tự làm):** trợ lý tra cứu SOP/FSSC theo kiểu agentic RAG sẽ tự quyết tra tài liệu nội bộ hay hỏi lại người, diễn đạt lại câu hỏi của trưởng ca thành thuật ngữ trong SOP, và trích nguồn cho từng câu trả lời — nhưng phải có cổng người duyệt và không tự trả lời khi truy xuất không đủ, đúng tinh thần "Chưa xác định" thay vì đoán.

## 6. Unit 4 — GAIA: benchmark có ngưỡng, leaderboard công khai

- **Cơ chế:** người học tự build agent và đánh giá trên một tập con của **GAIA benchmark** (bộ câu hỏi nhiều bước, cần tool use + suy luận + xử lý file, đáp án không mơ hồ). Đạt **≥30%** thì được Certificate of Completion; điểm được đưa lên Student Leaderboard để so với học viên khác. Khóa cảnh báo unit này thiên về thực hành nâng cao, ít hướng dẫn chi tiết hơn các unit trước.
- **Bài học thiết kế từ benchmark:** GAIA chấm **exact match** — đáp án thừa/thiếu một chút là sai, nên agent phải trả đúng định dạng được yêu cầu, không hơn không kém. Và bài học lặp lại từ các học viên đã làm: agent mạnh bằng **bộ tool của nó** (web browsing, đa phương thức, code execution, đọc nhiều định dạng file) chứ không chỉ bằng model — thiếu tool đọc file thì câu hỏi có file chắc chắn sai dù model giỏi.
- **Ánh xạ sang team:** cổng merge của team (validate PASS + device test code 0 + install code 200, PROTOCOL §4) là "GAIA của team" ở quy mô nhỏ: ngưỡng đạt viết thành luật, đo bằng máy, không chấm cảm tính. Khác biệt: GAIA đo agent trả lời câu hỏi, cổng của team đo sản phẩm build chạy được trên thiết bị thật. Điểm chung đáng giữ: **định nghĩa "đạt" trước khi làm**, và khi fail thì đọc trace để biết thiếu tool/bước nào (error analysis, task 132/140 §5) thay vì đổi model lớn hơn.

## 7. Bonus 2 — Observability & Evaluation: nhìn thấy agent đang làm gì

- **Nội dung:** gắn observability bằng OpenTelemetry cho smolagents; theo dõi token usage (chi phí), latency, error traces; đánh giá thời gian thực bằng phản hồi người dùng + LLM-as-a-judge; phân tích offline bằng benchmark dataset (vd GSM8K).
- **Vị trí trong mạch tự học:** đây là mảnh nối task 132 (evals: benchmark, judge hiệu chuẩn, regression) vào đúng framework của khóa này. Khóa 148 không dạy evals sâu như 132, nhưng đặt nó ở đúng chỗ: sau khi build được agent (Unit 2–3) và trước khi tin nó ở Unit 4. Thứ tự này khớp kết luận task 140 §5: đo từng thành phần + đọc trace lỗi trước khi thêm tính năng.
- **Ánh xạ sang team:** team đã có observability dạng thủ công — poll-log, task notes, STATUS.md, review chấm điểm /10 của chị cả. Chưa cần OpenTelemetry: quy mô 3 agent, việc chạy theo task rời rạc chứ không phải service liên tục. Bài học mang về chỉ là nguyên tắc: mỗi vòng lặp agent phải để lại trace đọc được (team đang làm) và chi phí/latency phải nhìn thấy được khi quyết định tăng tự chủ (team hiện chưa đo token theo task — ghi nhận là khoảng trống, không đề xuất làm ngay).

5. **Không đề xuất** lấy chứng chỉ hay nộp GAIA: chứng chỉ miễn phí nhưng cần làm bài thật trên tài khoản Hugging Face và chạy lab — ngoài phạm vi FREE của task tự học §9 (chỉ học nội dung), và team không có nhu cầu chứng chỉ.
