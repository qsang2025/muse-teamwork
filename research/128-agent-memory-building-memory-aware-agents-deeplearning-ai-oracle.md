## 1. Vấn đề: agent stateless hỏng ở nhiệm vụ dài hạn (Why AI Agents Need Memory)

- **Ba cách vá tạm phổ biến và vì sao chúng không đủ:** nhồi mọi thứ vào context window, nạp lại log hội thoại, hoặc gắn retrieval ad-hoc. Cả ba chạy được ở demo nhưng không cho một mô hình tư duy rõ ràng về việc thông tin nên sống ở đâu trong hệ thống. Context window lớn hơn chỉ cho model thêm chỗ làm việc *trong một phiên* — phiên kết thúc là context đi theo; nó không tạo ra tính liên tục qua các phiên.
- **Memory engineering — lớp thứ ba sau prompt engineering và context engineering:** hai lớp đầu tối ưu *một lần gọi LLM*; agent làm việc qua nhiều ngày/tuần cần một hệ thống bộ nhớ. Định nghĩa trục của khóa: bộ nhớ dài hạn là **hạ tầng hạng nhất — external to the model, persistent, and structured** (nằm ngoài model, bền vững, có cấu trúc). Ba tính từ này là ba quyết định thiết kế: bộ nhớ không nằm trong trọng số model (đổi model không mất bộ nhớ), phải sống qua restart/phiên, và phải có schema/metadata để truy xuất có chọn lọc thay vì đổ toàn bộ lịch sử vào prompt.
- **Phân biệt ba lớp hay bị trộn lẫn** (tài liệu Oracle đi kèm khóa nhấn mạnh): context window = bàn làm việc (thứ model đang thấy); RAG = tri thức ngoài (tài liệu công ty) nạp vào để trả lời có căn cứ; memory = trạng thái đã chọn lọc từ các tương tác trước, giữ để có tính liên tục. Hệ thống mạnh dùng cả ba, nhưng thay thế lẫn nhau thì hỏng: dùng RAG thay memory thì agent biết nhiều mà không nhớ người dùng; dùng context thay memory thì hết phiên là trắng.
- **Khi nào bộ nhớ thành bài toán dữ liệu:** ngay khi bộ nhớ phải bền + cách ly đúng người dùng + truy xuất tin cậy, các câu hỏi chuyển từ prompt sang dữ liệu: lưu cái gì, bỏ qua cái gì, gắn với user nào, mục cũ hết hạn/sửa/xóa ra sao, tìm đúng mục vào đúng lúc bằng cách nào. Đây là ranh giới mà task 127 chạm tới ở tầng framework (namespace, `actions_permitted`) và khóa này đi tiếp ở tầng database (metadata, vòng đời, quản trị).

## 2. Memory Manager và memory core hợp nhất (Constructing The Memory Manager)

- **Memory Manager là lớp điều phối duy nhất giữa agent và các store:** agent không tự đọc/ghi từng bảng; manager đóng gói mọi thao tác read/write/retrieve trong lúc chạy, để code của agent chỉ tập trung vào suy luận. Mẫu dựng lại của cộng đồng cho thấy hình dạng cụ thể: một class `MemoryManager` bọc hai backend — SQL cho episodic (lịch sử hội thoại, ACID, lọc theo `thread_id` + timestamp) và vector index cho semantic (sự kiện/tool, tìm theo nghĩa) — với các hàm `read_convo`, `search_knowledge`, `write_convo`. Điểm cốt lõi không phải class đó, mà là nguyên tắc: **mỗi loại memory có backend hợp với yêu cầu truy xuất của nó, nhưng agent chỉ nhìn thấy một giao diện**.
- **Bốn loại memory ở tầng hạ tầng** (khung CoALA mà tài liệu Oracle dùng — thêm *working* vào ba loại của task 127): working = trạng thái đang xử lý (messages, tool output, reasoning tạm); procedural = cách làm (chỉ dẫn, workflow, luật dùng tool); semantic = sự kiện đã học (sở thích, tri thức sản phẩm); episodic = sự kiện cụ thể đã xảy ra (phiên trước, lịch sử task, lần thử hỏng). Mỗi loại có yêu cầu độ trễ/độ bền/truy xuất khác nhau: working cần nhanh và được phép ghi đè; episodic cần truy vấn theo thời gian và lọc metadata; semantic cần tìm theo nghĩa cộng lọc chính xác; long-term cần bền, kiểm toán được, có kiểm soát truy cập.
- **Memory core hợp nhất (converged database) là luận điểm hạ tầng chính của khóa:** thay vì mỗi loại memory một hệ thống riêng (vector DB riêng, search engine riêng, DB quan hệ riêng) rồi tự đồng bộ, Oracle AI Database đặt cả bốn chiến lược truy xuất trong một engine: **vector search** (tìm theo nghĩa), **graph traversal** (suy luận theo quan hệ giữa các thực thể), **relational query** (bộ nhớ có cấu trúc, giao dịch, cần chính xác), cộng **JSON** cho episodic dạng sự kiện và **text search** cho từ khóa chính xác. Lợi ích được nêu: tránh data drift giữa các hệ, truy vấn hợp nhất được (join metadata hội thoại với vector tri thức tương tự), và vòng đời/bảo mật (hết hạn, lưu trữ, soft-delete, audit, cách ly tenant) dùng lại cơ chế database đã có sẵn thay vì tự chế.
- **Metadata là điều kiện sống còn của truy xuất:** mỗi mục nhớ phải mang `user_id`, `memory_type`, timestamp (và khi cần: `tenant_id`, ngày hết hạn) ngay từ lần ghi đầu tiên. Thiếu metadata thì không có cách tin cậy để biết mục nhớ thuộc về ai và còn đúng hay không — lỗi kinh điển là truy xuất nhầm bộ nhớ của user khác (rò rỉ chéo) hoặc mục cũ nổi lại. Bài học được tài liệu đóng khung thành câu: *chất lượng bộ nhớ phụ thuộc vào truy xuất đúng mục một cách sạch sẽ, hơn là lưu thật nhiều*.
- **Truy xuất lai (hybrid retrieval) thay cho vector thuần:** truy vấn thật thường chứa cả nghĩa lẫn định danh chính xác (tên sản phẩm, mã ticket, điều khoản, mã lỗi). Mẫu production: chạy song song vector similarity + keyword/text search + lọc metadata, rồi hợp nhất xếp hạng (ví dụ Reciprocal Rank Fusion). Vector thuần giỏi về nghĩa nhưng yếu về chính xác; keyword thuần thì ngược lại. Graph (`GRAPH_TABLE`) bổ sung chiều thứ ba: đi theo quan hệ (user → ticket → document) thay vì chỉ hàng xóm gần nhất theo nghĩa.

## 3. Tool như procedural memory — semantic tool retrieval

- **Bài toán mở rộng tool:** agent có hàng trăm tool mà nạp toàn bộ định nghĩa tool vào prompt mỗi lượt thì context phình, chi phí tăng, và model dễ chọn nhầm tool. Cách giải của khóa: **coi tool là procedural memory** — lưu mô tả tool vào một store có đánh chỉ mục vector, lúc suy luận dùng tìm kiếm ngữ nghĩa trên yêu cầu hiện tại để chỉ truy xuất vài tool liên quan nhất rồi mới đưa cho model. Tool từ "hằng số trong prompt" thành "dữ liệu truy xuất được theo nhu cầu".
- **Hệ quả thiết kế:** mô tả tool (khi nào dùng, tham số gì) trở thành dữ liệu phải viết cho *tìm được* — mô tả mơ hồ thì truy xuất sai tool dù tool đúng có tồn tại. Đây là cùng một kỷ luật với viết tài liệu để RAG tìm đúng, áp cho chính khả năng hành động của agent. Ranh giới an toàn của task 121/125 vẫn giữ nguyên: truy xuất chỉ *đưa tool vào tầm nhìn*, model vẫn chỉ *đề xuất* gọi, code vẫn là bên thực thi sau khi kiểm chứng tham số.
- **Nối với task 127:** ở 127, procedural memory là system prompt được viết lại từ phản hồi. Ở khóa này, procedural memory mở rộng thêm một dạng: **kho tool truy xuất bằng tìm kiếm ngữ nghĩa**. Hai dạng bổ nhau: prompt trả lời "phải làm thế nào", tool store trả lời "có những khả năng hành động nào liên quan tới việc này".

## 4. Memory Operations: extraction, consolidation, write-back

Ba pipeline LLM biến tương tác thô thành bộ nhớ dùng được — phần "tự học" của hệ thống:

- **Extraction (trích xuất sự kiện có cấu trúc):** thay vì lưu nguyên văn hội thoại làm "bộ nhớ", một pipeline đọc tương tác thô và trích ra sự kiện có cấu trúc (sở thích, quyết định, ràng buộc) kèm metadata. Lưu tất cả nghe an toàn nhưng tạo nhiễu: truy xuất càng nhiều mục rác thì chất lượng càng giảm. Quyết định "cái gì đáng là một mục nhớ" phải được chốt từ đầu, không để mặc định lưu hết.
- **Consolidation (hợp nhất episodic → semantic):** các trải nghiệm cụ thể (episodic) được chưng cất thành tri thức tổng quát (semantic) — ví dụ nhiều lần người dùng sửa cùng một kiểu phân loại thành một luật/sở thích bền. Mẫu kỹ thuật đi kèm: tóm tắt thread dài khi vượt ngưỡng (ví dụ 10 lượt), lưu bản tóm tắt thành mục semantic có vector, và đánh dấu các mục gốc bằng `summary_id` thay vì xóa — giữ được đường truy vết từ tri thức đã chưng cất về bằng chứng gốc. Hợp nhất là bước biến nhật ký thành tri thức; thiếu nó, bộ nhớ chỉ phình và tự mâu thuẫn (đúng vai trò background manager của task 127 §5, nay ở tầng pipeline dữ liệu).
- **Write-back / self-updating (vòng ghi-ngược):** agent tự ghi kết quả đã học ngược vào bộ nhớ — kể cả tri thức thu từ bên ngoài (kết quả tìm kiếm web được embed và lưu vào semantic memory: "tìm một lần, dùng mãi", giảm gọi API lặp). Vòng này bắt buộc phải xử lý **mâu thuẫn**: mục nhớ mới có thể xung đột mục cũ (sở thích đổi, sự kiện hết đúng), hệ thống phải có chính sách giải quyết (cập nhật tại chỗ, thay thế, hay giữ cả hai kèm ngày hiệu lực) thay vì để hai phiên bản mâu thuẫn cùng được truy xuất. Nội dung ghi ngược từ web phải được làm sạch trước khi lưu — bộ nhớ độc hại ghi vào store sẽ đầu độc mọi phiên sau (điểm bảo mật mà task 127 §7 đã nêu là khóa LangMem không bàn; khóa này chạm tới ở mức "sanitize trước khi lưu" và quản trị vòng đời, vẫn chưa phải một chương bảo mật đầy đủ).
- **Vòng đời là một phần của pipeline, không phải việc dọn dẹp sau:** hết hạn, lưu trữ, soft-delete, audit trail được thiết kế cùng lúc với schema (scheduler + chính sách cách ly theo tenant ở tầng database). Sở thích thay đổi, sự kiện hết hạn, lần thử hỏng cũ thành vô nghĩa — hệ thống không bao giờ cập nhật/loại bỏ mục cũ sẽ dần trả về ngữ cảnh cũ sai.

## 5. Lắp ráp Memory-Aware Agent và cách kiểm chứng

- **Agent hoàn chỉnh gồm ba nhịp:** (1) *khởi động* — nạp ngữ cảnh liên quan từ bộ nhớ dài hạn trước khi xử lý yêu cầu đầu tiên; (2) *trong lúc chạy* — vòng suy luận đệ quy có checkpoint trạng thái trung gian (nối thẳng checkpointer của task 125/127: hỏng giữa chừng thì khôi phục từ checkpoint thay vì làm lại); (3) *kết thúc phiên* — lưu ngữ cảnh đã học (qua extraction/consolidation/write-back) để phiên sau bắt đầu từ chỗ phiên trước kết thúc. Bộ nhớ phân tầng theo nhiệt độ khi quy mô lớn: hot (ngữ cảnh phiên hiện tại), warm (tóm tắt, episode gần đây, trạng thái task đang chạy), cold (hồ sơ lịch sử, sự kiện dài hạn) — giữ độ trễ thấp mà không mất chiều sâu lịch sử.
- **Kiểm chứng tối thiểu trước khi tin bộ nhớ** (bài ra mắt của Oracle đóng khung thành bài tập chấp nhận): chạy một bài tập của khóa, rồi **tái hiện một lần ghi + một lần nhớ lại trong một phiên mới hoàn toàn**; thêm **bài kiểm tra sửa và xóa** (correction + deletion test) trước khi dùng pattern với người dùng thật. Ba kiểm tra này bắt đúng ba lỗi chết người của hệ thống bộ nhớ: ghi mà phiên sau không nhớ lại được, sửa mà bản cũ vẫn nổi lên, xóa mà vẫn truy xuất được. Kèm theo là kiểm chứng chất lượng truy xuất sớm bằng vài truy vấn thực tế — truy xuất đã nhiễu ở 10 mục nhớ thì ở 10.000 mục sẽ tệ hơn, không tự tốt lên theo quy mô.
- **Khi nào không cần bộ nhớ:** tài liệu đi kèm khóa cảnh báo chống overbuild — agent hỏi-đáp một lần, người dùng không quay lại, hoặc retrieval tài liệu đã đủ thì một lớp bộ nhớ lớn chỉ thêm phức tạp. Bắt đầu bằng một loại memory có giá trị nhất (thường là semantic cho sở thích người dùng), phạm vi hẹp, metadata đầy đủ từ lần ghi đầu.

## 6. Đối chiếu với task 127 (Long-Term Agentic Memory with LangGraph)

| Khía cạnh | Task 127 — LangGraph + LangMem | Task 128 — Oracle AI Database |
|---|---|---|
| Tầng của bài toán | Framework: bộ nhớ gắn vào graph của agent | Hạ tầng dữ liệu: bộ nhớ là một hệ dữ liệu phải thiết kế |
| Đơn vị lưu trữ | `BaseStore` theo namespace (JSON + vector index tùy chọn) | Memory core hợp nhất: relational + JSON + vector + text + graph trong một engine |
| Ai điều phối | Memory tools (hot path) + memory manager (background) của LangMem | Memory Manager bọc các store; pipeline extraction/consolidation/write-back |
| Truy xuất | Tìm kiếm ngữ nghĩa trong namespace | Hybrid: vector + keyword + lọc metadata (+ graph theo quan hệ), hợp nhất xếp hạng |
| Procedural memory | System prompt được tối ưu/viết lại từ phản hồi | Thêm dạng thứ hai: kho tool đánh chỉ mục vector, truy xuất theo nhu cầu |
| Hợp nhất | Background manager sửa/xóa mục cũ (`actions_permitted`) | Consolidation episodic → semantic + tóm tắt theo ngưỡng, giữ `summary_id` truy vết |
| Mâu thuẫn & vòng đời | Nêu là mảng khóa chưa bàn (TTL, bảo mật bộ nhớ) | Có chính sách giải quyết mâu thuẫn, hết hạn/soft-delete/audit ở tầng database |
| Kiểm chứng | Không có chương đánh giá bộ nhớ | Bài chấp nhận rõ: ghi + nhớ lại ở phiên mới, kiểm tra sửa + xóa |

Hai khóa xếp thành một thang tiếp nối: **task 127 dạy agent nhớ cái gì và ghi ở nhịp nào → task 128 dạy bộ nhớ đó sống ở đâu, tìm lại bằng cách nào, và tự cập nhật ra sao mà không tự mâu thuẫn**. Khóa 127 trả lời ở mức "một agent, một người dùng"; khóa 128 trả lời ở mức "nhiều phiên, nhiều người dùng, chạy lâu dài" — nơi metadata, cách ly và vòng đời quyết định hệ thống có dùng được thật hay không.

## Điều học được, áp dụng được ngay cho việc chung

Áp dụng cho vai build (muse-1) và cách team muse-teamwork đang vận hành — team hiện chạy một hệ thống bộ nhớ bằng file + GitHub; khóa này cho thêm kỷ luật của tầng hạ tầng:

1. **Memory Manager của team = chị cả + bộ script (§2).** Agent (worker) không tự sửa board tùy tiện: claim/heartbeat/complete/sweep là giao diện điều phối duy nhất giữa worker và "store" (task file trên GitHub), đúng mẫu manager bọc backend. *Áp dụng ngay:* mọi thao tác đọc/ghi board đi qua script chuẩn thay vì sửa tay JSON — sửa tay là ghi thẳng vào store bỏ qua manager, mất kiểm chứng assignee/status mà script đã đóng gói.
2. **Metadata từ lần ghi đầu tiên (§2).** Task file đã có `assignee`, `status`, `claimed_at`, `claim_expires_at`, `updated_at` — chính là `user_id`/`memory_type`/timestamp của khóa này. *Áp dụng ngay:* khi ghi notes/result, luôn để script ghi kèm giờ và agent; một mục tiến độ không có giờ/người ghi là mục nhớ không lọc được, không biết còn đúng hay không (nối mục "sự kiện bền phải có ngày hết hiệu lực" của task 127).
3. **Truy xuất lai đã là cách team tìm tiền lệ (§2).** Worker tìm việc cũ bằng cả hai đường: grep từ khóa chính xác (tên site, mã lỗi, `first() !== null`) và đọc theo nghĩa (báo cáo research liên quan). *Áp dụng ngay:* khi quét chống trùng (PROTOCOL §3), chạy cả hai — tìm chính xác theo host/mã lỗi trước, rồi đọc báo cáo gần nhất theo chủ đề; chỉ tìm theo nghĩa dễ sót tiền lệ có mã định danh chính xác, chỉ grep thì sót bài học diễn đạt khác chữ.
4. **Tool/skill cũng là procedural memory truy xuất theo nhu cầu (§3).** Skill dùng chung của team đang lớn dần theo từng task tự học; nạp toàn bộ vào mọi phiên là "nhồi mọi tool vào prompt". *Áp dụng ngay:* worker chỉ đọc mục skill liên quan tới loại việc đang làm (site khó, merge, demo) thay vì đọc cả file mỗi lần — và khi đề xuất thêm mục skill mới, viết tiêu đề/mô tả cho *tìm được* (nêu đúng tình huống kích hoạt), vì mục skill không tìm thấy thì coi như không tồn tại.
5. **Consolidation giữ đường truy vết (§4).** Team đã hợp nhất episodic → semantic mỗi ngày: task file (episodic) → STATUS.md + skill (semantic) → MEMORY.md (chưng cất cao nhất). Mẫu `summary_id` của khóa nhắc: bản chưng cất phải trỏ về được bằng chứng gốc. *Áp dụng ngay:* mỗi dòng STATUS/skill rút ra từ một task nên giữ mã task nguồn (skill hiện đã ghi "(Task 127, ...)" — giữ đúng kỷ luật này); khi một kết luận bị sửa (như vụ bảng PUA fanqie ở task 108→109), ghi rõ kết luận nào thay kết luận nào thay vì để hai bản mâu thuẫn cùng sống.
6. **Write-back phải có chính sách mâu thuẫn (§4).** Worker ghi ngược kết quả vào task file mỗi ngày — đó là write-back. Chính sách mâu thuẫn của team là review của chị cả: kết quả mới xung đột kết luận cũ thì chị cả quyết và ghi rõ vào notes, không để worker tự ghi đè. *Áp dụng ngay:* khi bằng chứng mới phủ định ghi chép cũ, ghi mục mới kèm câu "thay thế kết luận X ở task Y" thay vì sửa lặng lẽ mục cũ — notes là nhật ký thêm vào cuối, không sửa mục cũ (PROTOCOL §8) chính là chính sách này.
7. **Kiểm chứng ghi–nhớ lại–sửa–xóa trước khi tin (§5).** Team đã có dạng của nó: `verify-spec.sh` kiểm tra spec không lệch, sweep dọn claim hết hạn, review chạy lại validate độc lập. *Áp dụng ngay:* sau khi ghi một sự kiện bền (skill/MEMORY), tự kiểm tra ba việc — phiên sau có tìm lại được không (đúng tầng, đúng từ khóa), khi nó hết đúng thì sửa ở đâu, khi cần xóa thì xóa có sạch không (không còn bản sao ở STATUS/skill). Sự kiện không qua được ba kiểm tra này thì chưa nên ghi thành bộ nhớ bền.
8. **Không overbuild bộ nhớ (§5).** Không phải việc nào cũng cần ghi thành tri thức bền: tiến độ một task ở lại trong task file, chỉ bài học dùng lại được mới lên skill. *Áp dụng ngay:* giữ kỷ luật "ghi đúng tầng" của task 127 — khóa này bổ sung lý do hạ tầng: mỗi tầng thêm vào là thêm một nơi phải đồng bộ, hết hạn và kiểm chứng; tầng không có người đọc thì chỉ sinh nhiễu truy xuất.

## Đề xuất cập nhật skill

Đề xuất cho muse-main xem xét (chưa tự sửa skill chung — skill do chị cả giữ, theo tiền lệ task 118–127):

1. **Skill `vbook-extension-building` — thêm mục "Truy xuất skill/tool theo nhu cầu" (từ §3):** trước khi build, chỉ đọc mục skill khớp loại việc (site khó / test-merge / demo) thay vì nạp cả file; khi đề xuất mục skill mới, mở đầu bằng tình huống kích hoạt cụ thể để worker sau tìm thấy bằng từ khóa của tình huống đó. Mục skill không tìm được thì không có tác dụng.
2. **Skill `vbook-extension-building` — thêm mục "Bản chưng cất phải trỏ về bằng chứng gốc" (từ §4):** mọi kết luận rút vào skill/STATUS từ một task phải ghi mã task nguồn; khi kết luận mới thay kết luận cũ, ghi rõ "thay thế kết luận ở task X" và giữ nguyên mục cũ trong notes (không sửa lịch sử). Đây là mẫu `summary_id` của consolidation áp cho file.
3. **Skill `vbook-extension-building` — thêm mục "Kiểm tra sửa + xóa trước khi ghi sự kiện bền" (từ §5):** trước khi đề xuất một sự kiện/quy tắc vào skill hoặc MEMORY.md, trả lời được ba câu: phiên sau tìm lại bằng từ khóa nào, khi hết đúng thì sửa ở đâu, khi cần bỏ thì còn bản sao nào khác không. Không trả lời được thì ghi vào task file, chưa lên tầng bền.
4. **Không đề xuất sửa PROTOCOL.md:** ánh xạ Memory Manager = chị cả + script, metadata = trường task file, consolidation = vòng task → STATUS/skill → MEMORY.md, write-back có chính sách mâu thuẫn = review của chị cả cho thấy cấu trúc hiện tại đã đúng mẫu hạ tầng của khóa; khóa này cho thêm kỷ luật truy xuất và kiểm chứng, không đòi luật mới. Cũng **không đề xuất** team dựng Oracle AI Database hay bất kỳ memory core nào — quy mô file + GitHub hiện tại là đúng tầng cho team 3 agent; bài học lấy ở khái niệm, không lấy ở sản phẩm.
